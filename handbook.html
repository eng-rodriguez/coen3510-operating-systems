1. Design decisions and open questions

Textbooks

Primary: Operating Systems: Three Easy Pieces (OSTEP)
Reference: Operating System Concepts, 10th ed.
Kernel: xv6 RISC-V book and source

Platform

POSIX C, Ubuntu/Linux, GCC/Clang, Make, Git, GDB, QEMU and xv6. Python optional for data plots.

Teaching principle

Predict → observe → implement → test → explain. Concepts precede complex kernel changes; xv6 appears in Week 2.

Pending institutional validation

Grade weights, final exam format, project scope, outcome targets, course policies and institutional ABET mapping.

Course description: Design, implementation and evaluation of operating systems, emphasizing hardware/software interaction; system calls, processes, threads, scheduling, synchronization, memory, file systems, I/O, protection and isolation. Students implement and evaluate C user-space programs and bounded xv6 kernel changes.

Scope control: The co-requisite is Advanced Programming, not a completed C prerequisite. Administer a Week 1 diagnostic and offer a short C bridge; do not presume pointer proficiency.

What must happen in class?

Require a minimum viable mechanism, one observed result, one individual explanation and an immutable checkpoint commit. For team work, each student answers an individual technical question. A student may show a partial implementation and still earn partial checkpoint credit by accurately diagnosing what fails.

What can happen at home?

Extended features, stress testing, benchmarks, documentation and cleanup. Home work is assessed with automated tests and a later short verification, not lengthy prose reports. Never require all code to be completed in the two-hour period.

Fast 4-point checkpoint rubric

PointsObservable evidence
1Prepared environment and baseline/prediction demonstrated
1Required mechanism or meaningful intermediate state demonstrated
1Test output or debugging trace interpreted correctly
1Student independently explains or adapts code to a small variation

Absence/accessibility: Provide equivalent supervised make-up demonstrations under an approved policy; ensure accommodations do not change the competency being assessed.

Scale: For 24 students, 2-minute defenses consume 48 minutes if sequential. Use simultaneous auto-checks, a TA, rotating oral checks, or a 60–90 second individual prompt to keep demonstrations feasible. Do not promise every student a lengthy oral defense every week.

4. Project briefs and gates

Project A — Mini Unix Shell

Weeks 3–5 · Process lifecycle, descriptors, pipes, errors

Minimum specification: Launch commands; handle fork/exec/wait; one pipe; redirection; nonzero exit status

In-lab gates: Week 3: execute one command; Week 4: pipe/redirection; Week 5: unseen test and explanation

Home scope: Parser complexity and multi-stage pipelines can be completed at home; no full job-control requirement

Suggested internal rubric: Unit/functional tests 60%, supervised defense 25%, design/quality 15%

Project B — Concurrent Work Queue

Weeks 6–8 · pthreads, race conditions, invariants, condition variables

Minimum specification: Bounded queue; no lost work; clean shutdown; no busy wait

In-lab gates: Week 6: reproduce race; Week 7: working condition-variable wait; Week 8: stress test and lock-order explanation

Home scope: Additional load tests, benchmarks, cleanup and documentation

Suggested internal rubric: Automated tests 55%, supervised invariant explanation 30%, experimental evidence 15%

Project C — xv6 Kernel Extension

Weeks 10–15 · System-call interface, kernel/user boundary, testing, engineering design

Minimum specification: Implement one bounded process-info syscall OR scheduling instrumentation; document constraints

In-lab gates: Week 10 design gate; Week 11 kernel trace; Week 13 test demonstration; Week 15 unseen test and individual defense

Home scope: Implementation, regression tests, performance study, reproducibility README

Suggested internal rubric: Automated tests 45%, supervised defense 30%, design tradeoffs 15%, reproducibility 10%

Universal project submission contract

Repository commit hash, build/run instructions, machine-readable test results, short design note (max one page), limitations, and AI-use disclosure. An instructor-selected unseen test and individual explanation verify ownership of understanding. Publish a reference test harness and clear failure messages.

Project dependency: A → B → C in increasing systems complexity; Project C must have a lower-risk approved option so students are not penalized for toolchain complexity rather than OS mastery.

6. AI-use and academic-integrity design

Practice: AI permitted

Students may ask AI for explanations, debugging hints, test ideas and code suggestions. They must inspect, test and understand anything they submit.

Lab checkpoint: independent verification

During a designated 60–90 second check, no AI assistance. Student predicts output, traces a path, fixes a small bug, or explains an invariant.

Individual exam: AI prohibited

Closed-AI supervised assessments test process tracing, scheduling calculations, concurrency reasoning, memory translation and design tradeoffs.

Recommended disclosure

Each project submission includes a concise AI-use statement: tool(s) used, task(s) assisted, and which generated suggestions were accepted or rejected. No requirement to submit entire chat transcripts by default; privacy and institutional policy take precedence.

Better than AI detection

Do not use AI-detector scores as proof of misconduct. Instead, use progressive commits, unseen tests, in-person explanation, small code perturbations, individual quizzes, and consistent rubrics. If a student cannot explain submitted work, grade the demonstrated learning outcome under a published policy; do not automatically infer misconduct.

Example individual check prompts

  • Predict how many times this line prints after two forks, and justify the possible output ordering.
  • Why must a condition-variable wait be inside a loop?
  • Which page-table entry bits explain this fault?
  • What happens to this pipe when the parent fails to close its write end?
  • Which test would distinguish a working scheduler from one that starves a process?

Simple testing, without CI/CD

Use instructor-provided make test scripts executed locally by students and by the instructor on the submitted commit. Public tests support practice; instructor-only edge cases support grading. Do not require or teach GitHub Actions, CI/CD pipelines, deployment, or workflow configuration. Record a reproducible test score and only review failures or exceptions manually.

Blackboard is the official submission and grading system

  • One Blackboard group submission per team for each lab report and final project report/presentation; configure group grades where supported.
  • Lab report: maximum one page or structured form with objective, observed result, test summary, GitHub URL, exact commit SHA, one interpretation, and brief AI-use disclosure. Do not require named team roles or individual contribution logs.
  • Homework and quizzes: individual Blackboard submissions. Record individual lab checkpoints and final defenses in the official gradebook.
  • Retain outcome-aligned rubrics and representative evidence for departmental ABET assessment.

GitHub is for basic team collaboration

Each team uses one private GitHub repository with starter code, README, Makefile, and tests. Teach clone, status, add, commit, pull, and push. Branches and pull requests are optional. The students decide how to distribute work; GitHub commit counts are not a proxy for individual learning or effort.

Final project: team deliverable, individual accountability

Require one team implementation, one Blackboard technical report (approximately 5–7 pages), and one presentation with a live demonstration. All students must participate in the presentation and individually explain part of the system during a no-AI defense. Project rubric: implementation and local tests 40%, technical report 25%, presentation/demo 15%, individual defense 20%. With four teams, allow approximately 10–12 minutes per team presentation plus separate individual defenses; adjust the schedule to actual enrollment.

AI policy

AI may assist team coding, debugging, planning, testing, and drafting, with a concise disclosure of material use. Students must verify outputs. No AI is permitted during individual supervised checkpoints, midterm, quizzes, or project defense unless specifically authorized or required by an accommodation. Do not use AI-detection scores as evidence of misconduct.
